# Glossary

Domain terms used throughout Ambi. Add new entries here when you introduce a concept that isn't self-evident from the name.

| Term                      | Meaning                                                                                                                                                                                                                                            |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Deck**                  | A collection of slides authored together. Plays as a sequence in a LiveSession.                                                                                                                                                                    |
| **Slide**                 | A single item in a deck, can be one of several types                                                                                                                                                                                               |
| **Slide Content Type**          | The polymorphic discriminator for a slide's `content` (`SlideType`/`@JsonSubTypes`, 17 values): `TITLE`, `CONTENT`, `MEDIA`, `INSTRUCTION`, `MCQ`, `TEXT`, `NUMBER`, `RANKING`, `SCALES`, `AXIS`, `GRID`, `MATCHING`, `ALLOCATION`, `PLACE_ON_IMAGE`, `DRAWING`, `Q_AND_A`, `FOLLOW_UP`. See `backend/src/main/java/com/cephadex/ambi/presentation/slide/enums/SlideType.java`. |
| **Slide**                 | An element with no scoring — title / section / callout / content / end variants. Used for presentation framing inside a deck.                                                                                                                      |
| **Question**              | A scoreable element. Each kind carries its own correctness shape and accepts a typed answer payload.                                                                                                                                               |
| **MCQ**                   | Multiple-choice question. Supports multi-correct — any non-empty subset of the listed options can be the "right" answer; an empty correct-options list is allowed but marks the slide unscoreable.                                                 |
| **AXIS**                  | Free-form 2D placement question: players place item chips anywhere on an X × Y plane with low/high endpoint labels; graded all-or-nothing by Euclidean distance to author-set targets within a per-slide tolerance (`INSIDE_RADIUS`). Continuous counterpart to GRID's discrete matrix. See [axis slides](features/axis-slides/README.md). |
| **PLACE_ON_IMAGE**        | Axis's sibling: players pin a single point on a backing image, graded correct if it lands inside any author-set target circle (`INSIDE_RADIUS`). Authoring surface only today — no live-session participant view, board, or results chart yet. See [place-on-image slides](features/place-on-image/README.md). |
| **DRAWING**               | Players freehand-draw on a shared 1:1 square canvas and submit a rendered PNG (stored in S3, referenced by the answer, not inline data). Always grades `correct = false` — a paired `BEST_ANSWER_VOTE` follow-up runs a full "most-picked" round on the submissions, but v1 awards no points from it. Implemented end to end (authoring, live board, results gallery). See [drawing slides](features/drawing-slide/README.md). |
| **AnswerPayload**         | Typed player answer (one `Answer` document per participant per round). Variants pair 1:1 with element kinds — except Q&A, which has two: `QAndAAnswer` is the wire shape of one submitted question, appended server-side into the stored `QAndAQuestions` aggregate (a player may ask several questions per round, but still just one `Answer` document). |
| **LiveSession**           | A live, hosted play session of a deck. Snapshots the deck's elements at create time so author edits mid-game don't desync clients. Tracks players, scores, and the current phase.                                                                  |
| **LiveSession phase**     | `RoundPhase`: `SUBMIT` → (`SUBMIT_LIVE`) → optional `VOTE` → `LOCKED`/`REVEAL_RESPONSES` → `REVEAL_RESULTS`. `VOTE` is the *current* round's own best-answer/deception voting (`openVoting`/`submitVote`; folds into `RoundEvaluator`'s `bestAnswer`/`deceivedCount` and scores on the `VOTE` → `REVEAL_RESULTS` transition) over its free-text/number/drawing submissions — not to be confused with **Best Answer mode** below, a different mechanism on a *different* round. See `backend/src/main/java/com/cephadex/ambi/session/liveSession/enums/RoundPhase.java`. |
| **Round timer / deadline** | A round's auto-close instant (ADR 002): `roundStartedAt + durationMs + accumulatedPauseMs`, from `LiveRoundState.deadline()`. Set only when the slide's resolved `AnswerSettings.countdownTime` is positive — otherwise the round stays untimed/host-driven. A leader-elected `DeadlineScheduler` polls a Redis ZSET and, on expiry, calls the same `closeSubmissions` transition a host click uses. The host can `pauseTimer`/`resumeTimer` (submissions stay open); a host presence loss auto-pauses a timed round and, absent reconnection, cancels the session after a grace window. See [ADR 002](decisions/002-live-session-round-timers.md). |
| **SessionFormat**, **AnswerSubmissionMode**, **ShowResponses cascade** | Not implemented. These only appear in an unused frontend file, `frontend/src/shared/types/SessionConfig.types.ts` (zero importers) — no `SessionFormat`, `AnswerSubmissionMode`, or `ShowResponses`/`showResponsesResolver` exists anywhere in the backend. Treat any reference to them as describing a frontend-only orphan, not a real feature.                                    |
| **Organization**          | A user-created group. Themes and decks can be scoped to an org (visible to all members). Users may belong to multiple orgs.                                                                                                                        |
| **Theme**                 | A curated palette (16 named colour roles — surfaces, text, brand, status) plus an intrinsic light/dark **appearance**, optional background + logo. Two layers: a per-user **global** theme paints the whole app; a deck's theme **supersedes** it on the slide canvas (editor only — the live session does not yet apply deck themes). "Ambi Light"/"Ambi Dark" are the app's built-in default appearances, painted entirely from `tokens.css` (`[data-appearance]`) — never DB rows; a deck/preference may hold their reserved ids (`ambi-light`/`ambi-dark`) but a lookup against the `themes` collection never sees them. The 6 remaining built-ins are real DB-backed presets after VSCode/terminal schemes (Catppuccin Mocha/Latte, Dracula, One Dark, Gruvbox Dark/Light). |
| **Best Answer mode**      | `FollowUpMode.BEST_ANSWER_VOTE`: a follow-up slide built off any scorable parent except `FOLLOW_UP` itself (MCQ, TEXT, DRAWING, NUMBER, RANKING, SCALES, GRID, AXIS, PLACE_ON_IMAGE, MATCHING, ALLOCATION) where participants pick the best submission *from the parent round*, run as the follow-up slide's own ordinary `SUBMIT` → `REVEAL_RESULTS` round — it never enters `RoundPhase.VOTE` (that phase is the separate, same-round best-answer/deception voting described above). A pick always grades `false` in v1 and awards no points; the reveal only badges the most-picked candidate(s). See [follow-up slides](features/follow-up-slides/README.md#runtime). |
| **Follow-up slide**       | A slide chained off a parent scorable slide (`Slide.parentId`/`childId`, server-owned) that builds its question from the parent round's submissions at runtime. Always sits immediately after its parent, moves with it as one unit, and is cascade-deleted with it. One per slide, no chains. See [follow-up slides](features/follow-up-slides/README.md). |
| **FollowUpMode**          | What a follow-up slide asks about its parent's submissions — `PREDICT_POPULAR` (MCQ parents: guess the most-picked option) or `BEST_ANSWER_VOTE` (vote for the best submission across any scorable parent: picked options on MCQ, free-form answers on TEXT/DRAWING, a compact text summary of the submission on every other scorable kind), or [`SPOT_THE_ANSWER`](features/follow-up-slides/README.md#spot_the_answer) (dixit-style: the parent's authored answer — the answer key's wording on TEXT, the `correctImage` picture on DRAWING — is seeded in among the submissions and the room has to spot it — the only mode that scores). Each mode declares its valid parent content types, plus whether it needs the parent to carry an answer key (`requiresAnswerKey`); the backend enum is authoritative, mirrored in `utils/followUp.ts`. |
| **Garage**                | Self-hosted S3-compatible object store running in Docker Compose. Backs all image uploads (avatars, theme logos/backgrounds, gallery images).                                                                                                      |
| **Auto-memory**           | Persistent agent state under `memory/` (not project docs). Excluded from `doc-lint`.                                                                                                                                                               |
